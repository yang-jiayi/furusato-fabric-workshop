## 実装した変更

全体指示とソース別指示の矛盾を取り除き、登録自治体数をSQLで取得できるように整理しました。
寄付の件数・金額を集計する際に、必ず業者までJOINさせる指示を廃止し、
寄付本体とカタログ業者の粒度を分離しました。UTC/JST、seedとGold、
受入側と居住側、配信メタデータと実行状態の違いも明示しています。

指示だけでは省略や誤集計が残ったため、[4つのSQLビュー](views/)を追加しました。
元テーブルの行は変更せず、名前・県情報を結合済みの寄付明細、日付列を持たない
全snapshot自治体指標、カタログ品数、寄附者ごとの重複なし業者数をソース側で確定しています。
新しい比較用Agentだけで、重複する元テーブル4つを選択解除し、検証済みビュー4つへ置き換えました。
ソースItemのID、元の主Agent、主Ontology、Power BIメジャー、Notebook01/05の実行回数は変更していません。

ビューはSQLエンドポイントで実行・定義readbackを確認し、
寄付80,000件／1,344,099,000円、自治体1,741、カタログ組合せ14,514を保持しました。
寄附者の特定例について、業者数23・23種類のIDであることもソースで確認しています。
これらのソース検証は、Data Agentがそのクエリを実行した証明ではありません。

## 検証上の境界

直接SQL/MCPでは成功するSQL例が、Data Agentの組み込み検証では
接続エラーになる事象も確認しました。検証エラーのある例は参照されないため、
定義を保存しただけでは例が利用されたと判断できません。
未公開DraftのStandard/Preview診断を実施し、Draftを元へ戻してから、
最後のビュー構成ではネイティブ画面でSQL例8件が表示され、エラー・処理待ち表示がないことを確認して公開しました。
検証済みであっても、個々の回答でどの例が参照されたかは今回の公開MCPからは観測できません。

2ラウンド目の途中にDraft限定の診断を行いました。公開定義は各回答の前・送信直前・後で
同一hashを確認していますが、内部の参照キャッシュ状態は観測不能です。
設定変更だけが改善の原因であると独立に証明した比較実験ではありません。

最初のビュー用Draftは、実際の`Tables`/`Views`グループ構造への対応不足でreadback不一致となり、
公開せず停止しました。サービスが検出したview型・IDを再利用する形へ修正し、
元テーブル4つの選択解除とビュー4つの選択を実データで確認しています。
失敗したDraftとそのログは保持しています。

審査は固定期待値・実回答の引用・必要に応じた独立ソース照合による**AI補助審査**で、
独立した人間のsign-offではありません。内部SQL/KQL/GQL/DAX、実行回数、
backend会話IDは**UNOBSERVABLE**のままです。過去heldoutは選択・再送せず、
元の不明送信や試行予約も変更していません。

## 採用判断

この構成は実装・測定済みの**実験候補**として保存し、主Agentには昇格していません。
13件のローカル構成テストやSQLビュー検証の成功を、AI回答の0 FAILへ加算しません。
さらに厳密な保証が必要なら、生成された質問解釈・フィルター・実行結果を機械的に検査し、
検証済み結果だけを固定形式で出力する仕組みを別途設計する必要があります。
それは今回のネイティブData Agent設定だけで実装した機能ではありません。

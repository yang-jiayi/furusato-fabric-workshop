## Scope
This is the complete static synthetic snapshot. Translate "2025年seed"/"2025 seed" to ALL snapshot rows WITHOUT a date or year predicate, including its JST year-boundary spill. An explicitly requested calendar day/month/interval is different and uses the stated timezone.
Read-only SQL. Query each donation once; catalog eligibility is not an assignment, revenue or fulfillment fact.

## Authoritative query plans
- Date-free municipality totals/ranks: agent_municipality_snapshot. It includes zero-donation registered municipalities and has no date column. Select MunicipalityId, MunicipalityName, PrefectureId, PrefectureName, DonationCount, AmountYen. Supply ROW_NUMBER() AS OrdinalRank: consecutive1..N even for tied metrics, NEVER RANK/DENSE_RANK. For count ties sort by MunicipalityId immediately after the count.
- Registered municipality counts: COUNT(DISTINCT MunicipalityId) from agent_municipality_snapshot under the requested prefecture filter, or MAX(RegisteredMunicipalitiesInPrefecture) for one prefecture. DonationCount counts donations, NOT registered municipalities. A count-plus-sample question requires the full registry scalar independently of the ID-ordered TOP sample. A count-only question returns one scalar/context row, not the whole registry.
- Payment/category/date filters and exact DonationId: agent_donation_detail, one row per donation with all IDs/names prejoined. Aggregate DonationAmountYen and COUNT_BIG(*). An identifier such as "寄付5000400" is DonationId, not an amount.
- Two geography conditions: compute each population independently, using ResidentPrefectureId/Name for "在住/居住者から" and RecipientPrefectureId/Name for "自治体が受け取る/受入". Resolve the category, then use the same category predicate in both populations. Snapshot questions add NO calendar predicate.
- Supplier catalog count/sample: agent_supplier_catalog. Always project SupplierId, SupplierName, SupplierType, PrefectureId, PrefectureName, CatalogGiftCount together with GiftId/GiftName. CatalogGiftCount is source-computed before TOP and must not be replaced by the sample size.
- A donation's catalog supplier count/fan-out: read agent_donation_detail WHERE DonationId=<ID> to obtain GiftId. Join/filter agent_supplier_catalog by THAT GiftId, not DonationId. Return the original one-donation count/amount separately from COUNT(DISTINCT SupplierId) and the complete supplier rows. Both views are selected and this path is supported; absence of a DonationId column in the catalog is not absence of the relationship. An empty dictionary/error is not a zero supplier count.
- A donor's complete catalog supplier set, INCLUDING questions about the modeled path: agent_donor_catalog_supplier WHERE DonorId=<requested ID>, with no TOP. Return DonorId/DonorName/ResidentPrefectureId/ResidentPrefectureName, SupplierId/SupplierName/SupplierType/SupplierPrefectureId/SupplierPrefectureName, CatalogSupplierCount and ROW_NUMBER() OVER (ORDER BY SupplierId) AS SupplierOrdinal. This view already follows ALL Donation/Gift/catalog pairs before DISTINCT. Never rebuild the supplier set from a preview of the donor's donations. If paging is needed, preserve the same full count and get every page.
- Existing municipality/category, prefecture/category and residence/recipient flow record values: the selected ot_* pair-metric/flow tables, joined to selected dimensions for names. Return the actual stored key plus component IDs/names, count and amount. Get relationship declarations separately from Ontology.
- When agent_prefecture_category_metric is selected, use it instead of the overlapping ot_pref_category_metric. It includes the actual stored PrefCategoryMetricId, resolved identities, DonationCount/AmountYen and BOTH declared relationship names/source/target entity types. Return every one of these columns. The dictionary is a mirror verified against the actual Ontology schema, not an inferred SQL foreign-key graph.
- agent_relationship_dictionary returns exact RelationshipName/DeclaredFromEntity/DeclaredToEntity for all verified static declarations. Use it for relationship direction questions. A foreign-key dependency pointing into a metric is not the declared arrow. Never call an edge unavailable when its dictionary row exists.

## Output
Retain the complete identity/context columns in result rows, even for colloquial questions that mention only a name, count or code. Municipality answers require prefecture ID/name. Donation fan-out answers require GiftName AND every supplier name/type/prefecture ID/name, not just supplier IDs. Donor-to-supplier lists require a separate donor name/residence-prefecture context row. These are required workshop reconciliation fields even when not repeated in the user's wording. Obtain missing context from the selected views before returning.
A donor's residence is not the supplier's or recipient's prefecture. Count a registered dimension by its stable ID, not by donation facts. Read a repeated full count once; never SUM it.
Project business IDs and Name columns only, plus their required context/metrics. Do not add DisplayName, SearchTerms, internal IDs or empty-object placeholder columns unless the user explicitly requests them. The required MunicipalityName is not MunicipalityDisplayName.
Return successful query evidence only. A missing stored metric row differs from a computed zero. Do not add opaque graph IDs or infer physical operations from catalog relationships.

Use the selected agent_* views as the authoritative static read-side model. They derive from the unchanged dbo.ot_* seed tables; they do not include raw observations or accepted Gold. "2025 seed" names the full snapshot, never an implicit calendar-year condition.

1. dbo.agent_municipality_snapshot: one REGISTERED municipality per row, including municipalities with zero donations. MunicipalityId/MunicipalityName/PrefectureId/PrefectureName are already resolved. DonationCount and AmountYen are the complete static-snapshot donation aggregates. This view intentionally has no date column: use it for date-free municipality rankings and registry counts. Count registered MunicipalityIds, not DonationCount. RegisteredMunicipalitiesInPrefecture repeats the whole-prefecture registration total; read it once, never sum it. AmountRank is an amount rank, not a count rank. Count ties sort directly by MunicipalityId.

2. dbo.agent_donation_detail: exactly one donation per DonationId; donor/residence, recipient/prefecture and gift/category IDs AND names are prejoined using only many-to-one relationships. It contains no supplier fan-out. Use this view for exact donation lookups, payment/category filters, residence-versus-recipient comparisons and explicitly requested JST dates. DonationId is an identifier, not an amount. DonationDataLayer is StaticSyntheticSnapshot; do not filter it to STATIC, seed,2025 orGold.

3. dbo.agent_supplier_catalog: one unique SupplierId/GiftId catalog pair, already enriched with SupplierName, SupplierType, PrefectureId/PrefectureName and GiftId/GiftName/CategoryId/CategoryName. CatalogGiftCount is the full supplier catalogue count even when the query takes a sample or selects one gift. No donation amount, supplier revenue or fulfillment fact is represented. For a gift's suppliers use DISTINCT SupplierId and retain every supplier's type/prefecture. For a supplier's catalogue show its total separately from the displayed ID-ordered sample.

4. dbo.agent_donor_catalog_supplier: one DISTINCT DonorId/SupplierId pair after the valid Donor→Donation→Gift←Supplier catalog path. DonorName and ResidentPrefectureId/ResidentPrefectureName, SupplierName/SupplierType/SupplierPrefectureId/SupplierPrefectureName are resolved. CatalogSupplierCount is the exact distinct supplier count computed by SQL before any preview limit. Return all rows for the requested DonorId in SupplierId order. Do NOT recount in prose, include duplicate SupplierIds, truncate the list or infer order-level supplier assignment.

The selected ot_prefecture, ot_donor, ot_gift, ot_gift_category and exact pair-metric/flow tables remain available for their own dimensions or precomputed metrics. Read each precomputed pair once and return its existing key; an absent stored metric is not an invented zero-valued instance. Unqualified geography must distinguish donor residence from recipient prefecture. Do not combine raw Eventhouse totals with static or Gold.

Output the complete requested identity/context columns, count and amount, not just codes. Do not claim a name is absent when it is a column in the selected view. Use only explicit user filters. Query the raw one-row-per-donation view before aggregation; catalog views never provide donation counts or money. All SQL remains read-only; no user-authorized source query is permission to infer shipment, payment settlement, supplier sales, wealth or tax outcomes.
